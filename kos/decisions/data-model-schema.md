Migrations/models for the entities in [PLAN.md](../PLAN.md)'s entity sketch.

### Users

Generated by `devise install` + `devise generate MODEL User` — do **not** hand-write auth
columns. Devise's own migration already adds `email`, `encrypted_password`,
`reset_password_token`, `reset_password_sent_at`, `remember_created_at`. An earlier plan draft
listed a hand-written `password_digest` column (that's `has_secure_password`'s column name, not
Devise's) — removed as a direct conflict with the chosen auth gem. Add only the app-specific
fields on top:

| Field | Type | Notes |
| :--- | :--- | :--- |
| name | string | `validates :name, presence: true` |
| bio | text | optional |
| profile_picture | string | plain URL (user pastes a link) — **not** a file upload; no Active Storage for MVP, see [[mvp-scope]] cut #3 |

### Posts

| Field | Type | Notes |
| :--- | :--- | :--- |
| user_id | bigint (FK → users, indexed) | `belongs_to :user` |
| body | text | `validates :body, presence: true, length: { maximum: 500 }` |
| created_at / updated_at | datetime | Rails timestamps |

Full CRUD for the owner: `edit`/`update`/`destroy` actions must check
`@post.user == current_user` (see [[implementation-guardrails]]) — index/show/create alone isn't
the full scope, per [[mvp-scope]].

### Follows

| Field | Type | Notes |
| :--- | :--- | :--- |
| follower_id | bigint (FK → users, indexed) | the user doing the following |
| followed_id | bigint (FK → users, indexed) | the user being followed |

Constraints (enforce in migration **and** model — don't rely on one or the other):
- Unique composite index on `[follower_id, followed_id]` — prevents duplicate follows.
- Model validation blocking `follower_id == followed_id` — no self-follow.

### Notifications

| Field | Type | Notes |
| :--- | :--- | :--- |
| recipient_id | bigint (FK → users, indexed) | who sees the notification |
| actor_id | bigint (FK → users) | who triggered it |
| action | string | e.g. `"follow"` (MVP has only this one value) |
| read | boolean | default: false |

Rule: never create a notification where `recipient_id == actor_id` (skip self-notification, e.g.
if follow-back logic is ever added). `action` will gain `"friend_request"` and `"friend_accept"`
once [[friend-requests-preview]] is picked up — not built now, MVP still ships only `"follow"`.

**How to apply:** build these four tables/models in the order given in
[[build-order-and-success-criteria]]. Three Phase 2 schemas are already sketched but **not built
now**: the Conversation/Message pair ([[direct-messages-preview]]), two enum columns on User for
post/comment privacy ([[content-visibility-preview]]), and the `FriendRequest` table
([[friend-requests-preview]]).
